### 2.1 为什么成交量要按板块分支

腾讯对同一列的语义不统一，实测：

| 标的 | 腾讯 2026-10-30 volume | 说明 |
|---|---|---|
| 000001.SZ 平安银行 | 1,864,245 | **手**（= 186.4 M 股，换手 ~0.96%） |
| 688981.SH 中芯国际 | 29,998,989 | **股**（= 30.0 M 股，换手 1.50%，与同花顺换手率一致） |

判定不是靠代码段猜，而是**价格锚定投票**：`成交额 ÷ 成交量` 若落在当日 `[low, high]` 区间 → 单位是股；
若 `成交额 ÷ (成交量×100)` 落在区间内 → 单位是手。每只取最近 8 个有效交易日投票，容差 ±5%。

**全量自证**（写入后用 SQL 对全表复算，不依赖脚本）：

| 检查 | 结果 |
|---|---|
| `volume_shares > 0` 的行 | 587,683 |
| 隐含均价 `成交额 ÷ 股数` **落在当日 [low, high] 内** | **587,417 行 = 99.9547%** |
| 越界 | 266 行（0.045%），**全部是「隐含均价正好等于当日最低价」的边界行**，越界幅度 < 0.01 元（成交额两位小数舍入所致） |

若某只标的的单位判错（手/股差 100 倍），该标的**全部**日期都会大幅越界——实测无此现象。
该方法同时是「元↔万元」10000 倍错位的检测器（错位后隐含均价会大 10000 倍，直接越界）。

板块分布（`tableoid` 实测）：主板 604 只 / 448,011 行，创业板 103 只 / 74,209 行，科创板 92 只 / 65,463 行。

### 证二：幂等 —— 重跑新增 0 行

| 场景 | 尝试写入 | 实际新增 | 冲突跳过 |
|---|---|---|---|
| 5 只 × 3 年（新 checkpoint 强制重跑） | 3,624 | **0** | 3,624 |
| 10 只 × 8 年（新 checkpoint 强制重跑） | 21,335 | **0** | 21,335 |

机制：`PRIMARY KEY (stock_id, trade_date)` + `ON CONFLICT DO NOTHING`，`RETURNING 1` 行数即真实新增。

### 证三：断点续传 —— kill 后续跑不重复不跳段

1. 10 只标的、`--start 2018-01-01`、全新 checkpoint 启动；
2. **运行 9 秒后 `kill -9`**：
   - checkpoint 落盘 **5 只**：`000651.SZ / 000333.SZ / 000858.SZ / 600030.SH / 002415.SZ`；
   - 库内实际：这 5 只各 **2,100~2,140 行**、最早 `2018-01-02`；未 checkpoint 的 5 只仍是 pilot 的 **726 行**（`2023-11-01` 起）。
3. 原命令重跑（同一 checkpoint）：`OK=5, SKIP_CKPT=5`，耗时 8 s；
4. 结果：10 只全部 `2018-01-02 ~ 2026-10-30`、**2,100~2,140 行/只**，无重复行（PK 保证）、无跳段（最早日 = 2018 年首个交易日）。

**「不跳段」的关键设计**：checkpoint 在**事务 COMMIT 之后**才写盘，所以
「已 checkpoint ⇒ 必然已入库」；反向的「已入库未 checkpoint」会被 `ON CONFLICT DO NOTHING` 吃掉。

### 证四：与存量热表全量交叉对拍（85,321 个重叠行）

| 维度 | 结果 |
|---|---|
| 重叠行 / 标的 | 85,321 行 / 799 只 |
| close **完全一致** | 788 只（**98.62%**） |
| close 有差异 | **11 只（1.38%）**，5,499 行 |
| volume 差异 | 77 行（0.09%），集中在 3 只银行股，**差 1 手（100 股）** |
| turnover 差异 ≥ 5,000 元 | 483 行（0.57%），差额均 ≤ 1 万元 |

**close 差异的定性（重要）**：这 11 只的差额是「分段常数、逐段递减、末端归零」，端点正好落在各自除权日——
这是**前复权的指纹**。即存量 `daily_quotes` 中这 11 只**仍是被 qfq 污染的**，而 `daily_quotes_hist` 是正确的不复权。

```
002594.SZ  422 行  2023-11-01~2025-07-28  差额 113.69 ~ 271.32
300308.SZ  604 行  2023-11-01~2026-04-29  差额   1.00 ~  55.85
600519.SH  519 行  2023-11-01~2025-12-18  差额  23.96 ~ 125.50
300750.SZ  598 行  2023-11-01~2026-04-21  差额   6.96 ~  18.78
601398.SH / 601288.SH / 601939.SH / 600941.SH / 000001.SZ / 688111.SH / 688036.SH  同型（差额 0.13~11.56）
```

**这不是本脚本的缺陷，而是存量数据缺陷的精确刻画**：98.62% 的标的在考察区间内没有除权，qfq 数值上等于 bfq，
所以抽样验证很容易「全部通过」；只有 1.38% 的标的能暴露出来。历史事故里「约 5.5% 标的价位错」即同一机理。
→ **切换 Reader 到 `v_daily_quotes_all` 之前必须先清这 11 只**（SQL 见设计文档 §7.5），否则会在分界处产生
最高 **271.32 元/股**的假跳空。

**volume 差 1 手 / turnover 差 ≤1 万**：属存量采集链路的舍入约定差异（`手` 由不同精度源换算、成交额「万元取整」
的进位方向不同），不是口径错误，量级 0.09% / 0.57%，记录备查。

## 6. 性能实测（两类主查询）

| 查询 | 计划 | 耗时 |
|---|---|---|
| (a) 单标的 3 年 K 线 `stock_id=? AND trade_date BETWEEN ? AND ?` | 3 个分区 `Bitmap Index Scan on *_pkey`，heap 命中 6 页/分区 | **0.90 ms**（683 行） |
| (b) 全市场某交易日聚合 `trade_date = '2025-06-10'` | 剪枝只留 `_2025` 分区，`Parallel Seq Scan` | **18.6 ms**（761 行，buffer 3,544） |

- 分区剪枝生效：查询计划里只出现 1 个（或 3 个）分区，5+ 个分区被剪掉；
- BRIN 在「单日等值」上未被规划器选中（分区内 243 天 × 761 行，等值选择度不足以赢过 32 MB 顺序扫），
  但代价近乎为零，且对「跨月区间扫描」有效，保留。

## 7. 环境与运维教训（下次全量前必读）

1. **上游限流硬阈值**：约 4,000 次请求 / 2.5 分钟（≈27 rps）即触发 501，cool-down > 4 分钟。
   全量 5,200 只必须 `--rps 6~8`，预计 5,200 × 5 请求 ≈ 26,000 请求 ≈ **55 ~ 75 分钟**。
2. **腾讯单次硬上限 800 根**：`--start 2018-01-01` 会被静默截断到 ~2023-07。
   脚本已实现「窗口回退翻页」（返回的最早日仍晚于 start 就以该日 −1 天继续拉），实测 8 年 2,140 根正确。
3. **腾讯双域**：`web.ifzq.gtimg.cn` 被限时 `ifzq.gtimg.cn` 仍 200，脚本会记住可用域。
4. **`_default` 分区会静默接住超范围数据**：本次 `--start 2018` 的 9,671 行先落进 `_default`。
   已按「临时表 → DELETE → CREATE PARTITION → INSERT」流程补建 2018~2021 分区并迁出，`_default` 归零。
   **全量前先确认分区覆盖到目标年份**。
5. **PG 客户端坑**：`node-postgres` 把 `date` 返回成 JS `Date`，`String(d).slice(0,10)` 会得到 `"Fri Oct 3"`。
   SQL 侧一律 `to_char(trade_date,'YYYY-MM-DD')`，脚本已修正。
