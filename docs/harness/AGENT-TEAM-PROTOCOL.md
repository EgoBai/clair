# 澄观 Clair 智能体团队协作协议 v1.0

> 2026-10-04 · 主理人制定。本文档是团队分工与协作的**稳定章程**（不随轮次变），
> 任务动态见 `TICKET-LEDGER.md`，阶段目标见 `EXECUTION-PLAN-*.md`。
> 设计意图：减少对人工干预的依赖，实现可持续自迭代的合理分工，支撑 RSI 迭代。

## 一、角色矩阵

| 角色 | 承担者 | 职责 | 权限边界 |
|---|---|---|---|
| **主理人**（team-lead） | 主 Agent | 整体规划、重要决策、开发计划、质量定调、合并收口（commit/push）、PLAN/DECISION_LOG 记账、自动化治理 | 最高；唯一对外（用户）出口 |
| **监工**（overseer） | 子 Agent | 推动并**独立复验**每个子 Agent 的进度与成果；维护任务台账；打回不达标交付；催办停滞；里程碑上报 | 不可改技术方向、不可 commit/push、不可动 PLAN/DECISION_LOG、不可改生产源码语义 |
| **执行者**（worker） | 按需派生的子 Agent | 按工单（Ticket）实现，自验后回报，接受监工复验 | 只许改工单声明的文件域；不可 commit/push |
| **红队**（red-team） | 按需派生 | 对抗性验证（证伪导向），只报告不修 | 只读生产源码 |
| **自主主循环**（automation-1784829898221） | 定时自动化 | 每 6h 一轮：自主改进池取项→执行→测试→记账→收口 | 单通道红线约束（见 §四）；无人在场时的默认推进者 |

## 二、任务工程体系（Ticket 制）

### 2.1 工单四元组（缺一不可，缺即拒收）
1. **目标**：一句话说清做什么、为什么（来源：PLAN.md 优先级 / DECISION_LOG 决定 / RSI 方案工单 / 评审报告问题项）。
2. **验收标准**：可机器验证的判据（测试数字、grep 结果、curl 状态码、行号、零 diff 声明），禁「看起来对」。
3. **文件域**：允许改动的文件清单；**零交集**为派工铁律。
4. **证据要求**：四证中至少几条（按改动性质）。

### 2.2 生命周期
`待派工 → 已派工 → 已交付(待复验) → 复验通过 → 收口(主理人 commit)` 或 `复验打回 → 执行者返工（≤2轮，仍败升级主理人）`。

### 2.3 台账（TICKET-LEDGER.md）
监工维护，每条工单记录：编号 / 来源 / 目标 / 验收标准 / 文件域 / 执行者 / 状态 / 复验证据 / 关联 commit。
台账是团队共享状态的唯一真源；任何人（含主循环）新增工单先登记台账再动手。

## 三、验证协议（四证）
1. **grep 证存在**（符号/路由/文件真实存在）
2. **读文件证逻辑**（实现与工单语义一致）
3. **curl/测试证行为**（端点状态码、定向测试数字）
4. **e2e/渲染断言**（页面级改动强制；curl 仅作存活探测，SPA 全路径 200 已证伪 curl 判可用）

- 子 Agent 自报完成**一律不信**，监工必须独立复验（曾两次实锤「自报完成≠落盘」）。
- 沙箱假失败纪律：并发负载下 vitest 会假超时，判失败前先空载单文件复跑。

## 四、单通道红线（防并行改库）
1. 生产源码（frontend/src、backend/src、shared、clair-worker、miniprogram）在途（M/??）→ 任何自动化/子 Agent **暂停源码推进**，仅容忍记账类脏文件（PLAN/DECISION_LOG/automation memory/guard 产物/报告产物）。
2. 主循环过期自动化置 ACTIVE 会立即触发一轮——**必须先 commit/push + 确认工作树干净**再启用。
3. 在途超 24h 未收口的生产源码 → 按 D22 接管规则由主理人核验后收口。
4. dashboard 自动化（automation-1786816465504）的框架级 `git stash -u` 行为已两次实锤破坏在途工作——**保持 PAUSED 直至框架修复**，任何人不得擅自启用。

## 五、RSI 迭代闭环接入
- **研发侧**（既有 8 步 Loop：SCAN→EVAL→PLAN→EXEC→VERIFY→CAPTURE）由主循环承担；人工会话活跃时由主理人承担，主循环让路（单通道）。
- **用户侧**（发掘→筛选→自选→复盘+验证，D26-1 收窄案）已落地最小闭环：复盘快照 + 超额收益基准 + 兑现判定（R0'-6，ReviewPage）。
- **评估器不可复用**原则：研发侧=确定性机读真值；用户侧=延迟/噪声/多因子混淆，信号累计 ≥200 条且用户体系启用前，用户侧不做 bandit/judge，触发式重启（D26-1）。
- **任务工程即评估器**：每张工单的验收标准就是研发侧 RSI 的 reward 函数——工单制让 RSI 从口号变成可复验的机器闭环。

## 六、记忆纪律
1. 交付即记：完成实质工作立即追加 `.workbuddy/memory/YYYY-MM-DD.md`（项目工作区）。
2. 决策即录：重大决策进 DECISION_LOG.md（主理人）；用户拍板类标「待用户决策」。
3. 台账即真相：跨会话状态以 TICKET-LEDGER.md + PLAN.md 为准，禁止直引口头记忆/过期台账数字（两次实锤教训：「20 只 mock」「IP-12 待做」均为滞后记录）。
4. 任何清单派发前以源码实测复核。

## 七、升级路径
- P0 阻断 / 产品决策 / 资源投入 / 技术选型 → **主理人 → 用户**。
- 验收打回 2 轮仍败 / 子 Agent 停滞催不动 → 监工上报主理人。
- 连续 5 轮无可做项 → 主循环标记停滞并推送提醒用户（防空转机制沿用）。
