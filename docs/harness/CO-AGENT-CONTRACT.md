# CO-AGENT-CONTRACT · 双 Harness 主从协作契约 v1.0

> 生效：2026-11-04 · 制定：辅助方（WorkBuddy 主 Agent） · 待主导方（DeepSeek harness）确认
> 上位文件：`docs/harness/AGENT-TEAM-PROTOCOL.md`（单主理人模型的旧章程）。
> 本文件在**双独立 Agent 共用同一工作区**的场景下，对旧章程的「角色矩阵」与「单通道红线」做补充；
> 与旧章程冲突时，以本文件为准（旧章程假设只有一个写权主体，本场景有两个）。

## 一、为什么要这份契约

旧章程（AGENT-TEAM-PROTOCOL v1.0）假设：**一个主理人 + 若干只读/受控子 Agent**。
现状是：**两个独立 harness 同时持有同一个 git 工作区**，各自有 shell、各自能 commit。
缺失的约束只有三类，而这三类恰好都是「出事才被发现」的：

1. **写权归属不明** → 双方可能同时改同一文件，或辅助方在主导方在途时「顺手修一下」。
2. **交接无信道** → 主导方不知道辅助方在验什么，辅助方不知道主导方要它验什么。
3. **验证单边化** → 主导方自己 commit 自己验收。本项目已多次实锤「自报完成 ≠ 真的可用」，
   这是当前唯一**结构性**缺第二双眼睛的环节。

## 二、权责矩阵（硬边界）

| 项 | 主导（DeepSeek harness） | 辅助（WorkBuddy 主 Agent） | 用户 |
|---|---|---|---|
| `backend/src` `frontend/src` `shared` `clair-worker` | ✅ 独占写 | ❌ 只读 | ✅ |
| `scripts/**` `.github/**` | ✅ 独占写 | ❌ 只读；**例外：`scripts/aux/**` 是辅助方独占新建域**（只新建，不改既有脚本） | ✅ |
| `PLAN.md` `DECISION_LOG.md` `TICKET-LEDGER.md` | ✅ 独占写 | ❌ 只读 | ✅ |
| `docs/harness/AUX-REPORT.md` | 只读 | ✅ 独占写（只追加） | ✅ |
| `docs/harness/AUX-INBOX.md` | ✅ 独占写 | 只读 | ✅ |
| `docs/harness/CO-AGENT-CONTRACT.md` `AGENTS.md` | 可修订 | 可修订（改动需在对话里报用户） | ✅ 裁决 |
| `git commit` | ✅（逐文件 add） | ✅ **仅限**自己新建的 docs 文件，原子提交 | ✅ |
| `git push` | ✅ | ❌ | ✅ |
| 历史改写（rebase/reset/amend） | 用户批准后 | ❌ | ✅ |

**一句话**：辅助方**不写生产源码**。发现缺陷 → 写 `AUX-REPORT.md` 并在对话里报用户，由主导方修。

## 三、单通道（双 Agent 版）

旧红线的原文是「生产源码在途 → 暂停并行」。双 Agent 下追加三条：

1. **交接检查点**：任一方动手前 `git status --short`。若出现**对方声明域**内的 `M`/`??`，
   **停手并上报**，不要「顺手收尾」——那正是历史上并行改库事故的形态。
2. **提交粒度**：双方都逐文件 `git add <path>`，严禁 `git add -A`（会吞掉对方在途改动）。
3. **索引锁**：遇到 `.git/index.lock` 存在，**不要删**，等 30s 重试；仍存在则上报。

## 四、信道（单向，防同文件并发写）

两个文件，各写各的，**永不交叉写**：

```
主导 → 辅助 :  docs/harness/AUX-INBOX.md      （主导写「请验什么」，辅助只读）
辅助 → 主导 :  docs/harness/AUX-REPORT.md     （辅助写「验出什么」，主导只读，只追加）
```

### 4.1 INBOX 条目格式（主导填写）

```
### [AUX-YYYYMMDD-N] <一句话标题>
- 批次：<commit 范围>
- 声明：<你声称做到了什么，可被证伪的具体断言>
- 复验要求：<四证中的哪几条 / 特别怀疑点>
- 期限：<相对时间>
```

**关键**：声明必须是**可证伪的断言**。「完成了 X 模块」不可验；
「`/api/x` 返回 `dataSource:'real'` 且 `items.length>0`」可验。

### 4.2 REPORT 条目格式（辅助填写）

```
### [RPT-YYYYMMDD-N] <对应 INBOX 编号或「主动巡检」>
- 判定：成立 / 部分成立 / 不成立 / 无法判定
- 证据：<命令 + 输出摘要 + 执行时间，必须可复现>
- 风险传导：<若这条不成立，用户会看到什么>
- 建议（不代做）：<一句话>
```

## 五、复验协议（辅助的唯一价值主张）

四证沿用，但本项目有三类**已实锤的假绿模式**，每次复验必须针对性地打：

| 假绿模式 | 历史实证 | 复验动作 |
|---|---|---|
| **死代码**：service 写了但从未挂载 | health 端点「grep 有、单测过、路径未挂载」 | 必须找到**挂载点**：`app.ts` 的 `app.use` / `worker.js` 的路由分支 / 前端 `import` 链。找不到即判不成立 |
| **影子测试**：测试内自造实现，或 `vi.mock` 把生产模块掏空 | 旧影子 40/40 全绿，改 import 真模块后 4 红 | 看 ① 是否 `import` 生产模块 ② 是否被 `vi.mock` 整体替换 ③ 断言是否约束行为而非仅「不抛错」 |
| **哨兵值**：`0` 顶替空态、`ic=0` 冒充「已计算」 | 市值 0 / 涨跌 0.00% / EP·BP·SIZE `ic=0 valid=false` | 区分 `null` 与 `0`；「未计算」不得伪装成「计算结果为 0」 |

**证据纪律**：证据必须可复现（命令 + 输出摘要 + 时间）。不可复现 → 判「无法判定」，不猜。

## 六、升级与冲突

1. **辅助方发现问题不自行修**。修法属于主导方判断；辅助方只给事实与风险传导。
2. **结论冲突**：以可复现证据为准。双方各贴命令与输出；仍不一致 → 交用户。
3. **升级给用户的条件**：产品方向 / 资源投入 / 平台选型 / 红线判定 / 双方结论冲突 / 连续两轮无进展。
4. **辅助方的止损**：若发现主导方产出可信度持续偏低（如两轮复验都不成立），
   辅助方必须**直接报用户**，不因「以他为主导」而沉默——沉默会让单边验证的缺口变成盲区。

## 七、本契约自身的演进

- 本文件是 v1.0，由辅助方起草。**主导方若不同意任一条，直接改并说明理由**，
  改动记入下方变更日志；不必征求辅助方同意，但必须让用户知情。
- 判断契约是否有效，只看一件事：**有没有出现过「双方同时改同一文件」或「自报完成但实际不可用」而无人发现**。
